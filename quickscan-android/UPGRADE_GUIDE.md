# 快递快扫 | 后续升级操作说明

## 界面版源码与构建

- 仓库 `603141335-lgtm/ai-manju-workbench`
- 维护分支 `quickscan-v0160-ui`
- 工程目录 `quickscan-android/`
- 构建命令与界面设计见 [界面改版说明](UI_V0160.md)。

## 版本与包名

- 每次发版递增 `versionCode`，同步更新 `versionName`。
- 交付的独立安装包使用 `com.kuaidi.quickscan.ui`。原有数据存于旧应用。
- 使用原包名覆盖升级需要旧版对应的签名私钥。原签名不可用时可以使用独立包安装，旧应用继续访问原记录和照片。
- 签名密钥保存在受控的构建环境中。

## 重点回归测试
1. 一维条形码连续扫描准确；不识别二维码。
2. 成功/重复/失败语音及震动是否正确。
3. 模糊条码拍照成功且关联当前批次。
4. 照片打开全屏、双指放大、分享、另存能用。
5. 批次选一张或全选删除照片；确认照片文件实际消失，单号/时间/备注保留。
6. Excel 完整明细与仅单号真实是 xlsx；在 WPS/Excel/腾讯文档打开正常；前导零和长数字不变。
7. 系统选择应用分享时授予临时文件读取权限。
8. 原有数据在升级前后能否继续访问，绝不假设自动迁移。
9. 记录 GitHub Actions 构建运行链接、结果和已知问题。

## 文件安全
- SQLite：`ScanDb.kt` 对应应用内部数据库。
- 图片：`files/photos`。
- 临时分享的 Excel：`cache/exports`。
- 卸载应用会清理该应用私有文件和数据库。Excel 不包含照片文件本身。
- 云端构建的 Artifact 默认 30 天到期；真正需要长期 APK 分发需另建正式发布流程。

## 重要：扫码准确性策略（v0.12）

1. 不再“检测出一帧就入库”，需连续 8 帧候选一致且画面中心、形状、单号长度符合限制。
2. 人工核对纸面打印的单号后按确认键才写入数据库；怀疑时先拍照再手动补录。
3. 默认仅支持常见 CODE128 和 ITF；其他物流条码格式可能不再被识别，发现必要的码型时要先实测再扩展，不能一概添加所有码型。
4. 同号复扫在经过扫描验证后提示“重复”，但识别算法无法在所有设备光照条件下 100% 保证正确；需用真机回归测试与真实标签验证。

## v0.12 自动快扫校验

- 连续多帧一致后直接登记、播报、拍照，不再手动点确认。
- CODE128: 3帧且跨至少80ms；ITF: 4帧且跨至少140ms。相机实际处理帧率决定最终用时，不能保证固定速度。
- 锁定镜头中的同一条码直到条码移开；同号重新进入时反馈重复。仍不能承诺识别准确率100%，必须用实际标签抽检。
- 数据库变为 version2，迁移时只创建复合索引，不删除旧记录。
- 照片保存前暂停下一次识别以确保照片关联正确，这是留图需求对速度的限制。

## v0.12 重点回归
1. 同一批次扫完全相同单号，重复通知但数据库无重复行；新库部分唯一索引 `idx_unique_batch_code` 生效。
2. CODE128 连续两帧、ITF 连续三帧识别；快扫时注意错误近似单号仍可能是不同合法字串。数据库去重不等于误识别率为零。
3. 每次自动拍照结束后播报“成功”；照片失败时保留单号和补拍入口。
4. 首页/批次/扫码列表以及 Excel 保存、分享、打开正常。数据库 schema 3 升级时不能删除已有数据及照片。
5. 当前调试 APK 使用独立包名，不覆盖旧版且数据不能自动迁移；需要正式签名和备份迁移才能做到后续无损升级。
